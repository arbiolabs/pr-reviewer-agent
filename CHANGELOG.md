# Changelog

This file records every notable change to pr-review. Its format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html). The version covers the CLI, the service, the daemon, the terminal client (`tui/`) and the version 1 protocol between the client and the daemon.

## [Unreleased]

### Added

- **Real-PR eval.** `pnpm eval:snapshot` saves the open PRs of a repository, their inline review comments and reviews, and a full bare clone to a gitignored dataset directory, using GitHub GET requests only. `pnpm eval:real` reviews each saved PR offline in dry run, and refuses to start when the publish mode is not `dry_run` or a review would get `--publish`. `pnpm eval:report` reports overlap with the human comments on the head commit, run-to-run stability, Jev routing, the verifier's discards and cost proxies, and writes a grading sheet whose verdicts give a precision number. See `bench/REAL.md` (#28).
- **Eval: another AI reviewer as a comparator.** The real-PR eval sets apart comments from [pr-review-agent](https://github.com/vikrrantshah/pr-review-agent), which posts from a person's account and so read as human labels, compares its findings with pr-review's, and puts them on the grading sheet. The sheet also lists the candidates the verifier discarded (#30).
- **Resolved findings.** The review request lists the open findings of earlier reviews with their ids, where each was last seen, what the new commit did to its cited code, and that code as last seen, capped at 200 characters a line and 40,000 bytes in all, with paths and titles shown as one-line data. The model can claim a finding fixed in `submit_candidates`, with head-side code evidence, and code checks the claim the way it checks a finding: none of the finding's own cited code may survive at the head, in its file or anywhere in the tree, compared as code tokens, so a comment, a blank line, re-indentation, a dropped semicolon, a changed helper or a line moved into another file is not a fix; no candidate of the same review may report it again or still cite six or more tokens of its code, whether or not that candidate passed verification and whatever its anchor or file (a handler that stays reachable through a second unguarded route is not fixed); and the evidence must exist at the head commit, cite code rather than a comment or a blank line, sit in the finding's file (or in a file the PR changes, when that file is gone), and neither sit whole in the finding's own code nor hold all of it. Code cannot tell a real fix from a rename, so past that line the status rests on the model's claim. A second claim on the same finding is refused as a duplicate and does not outvote the first. An accepted claim moves the finding to `RESOLVED`, which the review body lists under "Looks resolved since the last review" and `pr-review inspect` shows with the verdict on every claim. Under `silent_no_findings`, a commit with a newly resolved finding posts. A defect that comes back after `RESOLVED` is a new finding with a new inline comment. Migration 056 stores the claims and verdicts (#31).
- **Self-correcting resolution.** A resolved finding stays watched for the life of the PR. Each later commit's review runs the same code-survival check on it, and if its code is still there the review reports it again as a new finding, with one new inline comment when its line is in the diff and a line under the new findings otherwise, reading "looked resolved at `<commit>`, but its code is still here". So a resolution the check got wrong lasts one push. Each resolved finding is reopened at most once, a re-report by the model in the same review joins the reopened finding instead of adding another, and the watch covers the 50 most recently resolved findings of a PR. Under `silent_no_findings` a reopen posts. `pr-review review --json` and `inspect --json` name the resolved finding under `reopens`, the finding history's `basis` reads `reopened` on the first entry, and the benchmark prints a `reopened` column. Migration 057 records which resolved finding a new one reopens (#31).
- **Same code, every reading.** The resolution check tokenizes the head file and the stored text from the same normalized lines, so a string with two spaces, a multi-line template literal, or an unterminated quote before trailing whitespace or CRLF no longer reads as changed code. It compares under four readings of a backtick, `/*` and `--`, which may open a string or comment or sit in a regex, a shell glob or a decrement, and takes any match, so an unrelated line added above the defect cannot swallow its tokens. Escaped quotes inside strings and the case of numeric literals are folded, so Prettier's rewrites are not changes. A line with no code tokens, such as a `#apiKey` field or a `--flag \` line, is found as written anywhere in its file. The tree-wide search reads files git calls binary. Finding the longest shared run of tokens is linear in the file instead of quadratic (200,000 repeated tokens took 132 s, now under a second), each file is tokenized once per review, and a file over 4,000,000 characters is compared by its lines only, which keeps the finding open (#31).
- **Reopen only on strong evidence.** The watch on a resolved finding reopens it only when its distinctive code (six tokens under every reading) is back in its file read as code, with its shorter items in place: a true fix followed by an unrelated short line such as `return ok;`, a `}` at a new line, or the old statement quoted in a `/* */` block or after a SQL `--` no longer reopens the finding and posts its text on unrelated code. Refusing a resolution claim still counts every reading, every match and the lines as written. An item is substantial enough for the tree-wide search when some reading gives it six tokens, so a regex backtick or a shell glob in the cited block no longer hides a moved line from the search. A finding's code in a file over 4,000,000 characters whose lines are not found as written is unknown rather than gone, which refuses the claim, and a blob over 16 MB is not read at all: it counts as present with unknown contents, where before `git show` failed the review on every head of a repository that holds one. A review retains about 90 MB after searching 1,500 files of 11 KB instead of 1.4 GB, and each search for a finding's text in a file runs in time linear in the file (2.7 s per watched finding on a pathological file, now 0.8 s). A reopening whose own review never reached GitHub, because a newer push superseded it, is listed as new with its "looked resolved at" line by the next review that carries it, and counts as news under `silent_no_findings` even when its line is off the diff (#31).
- **Re-reports by id.** A candidate can name the open finding it reports again with `priorFindingId`. Code accepts the link only where it can see the report: within three lines of the finding's anchor at this head, or of its own text found in the file the candidate reports when its code was not found, and citing lines that overlap that evidence; the name alone never links. A named re-report that fails verification leaves a doubted finding `UNCERTAIN`, listed under "Uncertain, reported again without verifiable evidence". A finding is found again by its code tokens, so one distinctive line such as `db.orders.delete(id);` is followed into another file and a moved block whose lines were re-aligned is still found. The request spells out format characters, such as a zero-width space, in prior titles and paths, and folds fullwidth lookalikes before it defuses a closing fence. The benchmark prints each review's resolution verdicts, and `bench/baselines/checked-resolution-2026-10-22.json` records three runs of the multi-commit cases after this change (#31).
- **Desktop client foundation.** `desktop/` holds `pr-review-desktop`, a macOS app on GPUI through gpui-kit 0.8.0 that runs the terminal client's reducer and network task unchanged and shows the connection state and the PR list. It takes the client's `--socket`, `--pr`, `--playback` and `--config` flags. `--snapshot OUT.png` captures its own window without a Screen Recording grant, and with `--playback` the script plays in virtual time, so the same flags give the same pixels; `--actions` drives it with steps such as `down,open,goto:diff,wait:300`, and `desktop/snap.sh` renders named states of the showcase. The terminal client gains `Msg::Action` and `Msg::Pick`, which run an action or a click target without a key or coordinates, under the same guards. CI builds, tests and smoke-tests the harness on macOS (#32).

- **Desktop: the triage inbox.** `pr-review-desktop` opens on a queue of decisions instead of a PR list: a parked review to approve and post, the PR with the worst open finding, a failed review to retry, a PR no review has looked at, and a setup gap that keeps reviews from running. Selecting a card opens its detail: the PR's findings, a finding with its cited code, evidence, reasoning, fix and history, the exact publication preview with a two-step post (⌘⏎), or the run working live with its phase stepper and activity. Running reviews sit in a live strip, the diff anchors each finding under its line, ⌘K opens a command palette, and the done list holds what is posted, clean or merged. Color, type, spacing, radii and motion come from one token module with a WCAG AA test; `desktop/DESIGN.md` explains them. `snap.sh` renders the design states in dark and light, and `--actions` gains `tab:done`, `palette:QUERY` and `keys`. The app follows macOS Reduce motion (#TBD).
- **Desktop: the second review's changes.** Code never cuts mid-token: evidence, fix and comment blocks scroll sideways under a right-edge fade, and the diff soft-wraps at a space, a comma or a bracket with the continuation indented under its line. The action bar is a row of the layout with a hairline and a fade over the scroll end. Cards put the meta line and the action on their own rows, finding rows wrap their meta, hover is a tint, focus a ring 2 pt off the control, and only the selected card carries a stroke. The post sheet follows macOS: Cancel is the default on esc and ⏎, the filled red Post acts on ⌘⏎, the scrim is 40 %, and the page's own Post dims under it; canceling a review asks the same way. A failed run colors only the phase it stopped in and names the reason once. Setup speaks one vocabulary ("1 blocking · 2 limited") and renders a fix's commands as copyable chips. The live strip gives each pill its title and steps aside on a finding, the proof, the diff and setup. The sidebar sets titles on their own lines with one accessory slot. Light hues deepen, chips and badges gain an outline, disabled controls are outlined grey, and the AA test covers chips over their wash, disabled text and its outline, the diff washes and the code gutter. Numbers use tabular figures. The timeline aligns a fixed tool column and a 16 pt glyph slot; the palette sets matched characters bold and leaves an empty shortcut slot blank. The empty queue shows the done list under "You're clear" instead of a blank column beside a populated pane. The offline card centers and spins while it retries, the connecting skeleton mirrors the loaded layout, a finding with no evidence says "No code cited", the published proof says it once, and ⌘⇧O opens GitHub so ⌘O stays the platform's. The window blurs the desktop behind its sidebar and title bar; a snapshot stays opaque (#TBD).
- **Desktop: the design review's changes.** One title bar holds the traffic lights, the page title, a one-sentence state ("One review is waiting on you. #1287 has a critical finding.") and the ⌘K field. The sidebar lists every PR by repository with a state glyph, a status word, a severity count and a phase gauge. A finding opens in two columns: the argument at a reading measure, then the evidence pinned to its path, lines and commit, the tool summaries and the diff hunk; code wraps with a continuation mark instead of clipping, and the lexer carries block comments and template strings across lines. The live page gets a scrubbable track of every event, colored by kind, with "following" and "replaying N of M". The timeline is a tab of the PR page, sectioned by phase. Posting asks once more in a sheet that names the account, the commit and the counts, with Cancel as the default and ⌘⏎ to post; canceling a run asks too, while starting and retrying go straight through. The palette keeps unavailable actions visible with the reducer's reason and ranks prefixes and initials first. Page and PR titles are set in the system serif. Offline, connecting, clear, no-findings, too-large and read-only states are designed, and an offline window never claims the reader is clear. Every control is a tab stop with a focus ring, hover and pressed states, and icon buttons carry tooltips. `--actions` gains `confirm-post` and `scrub:N`, and `snap.sh` renders the new states. A snapshot ignores the keyboard and the pointer, activates its window before each capture, retries a frame that never presents and a run that never writes its PNG, so the same state captures to the same bytes with the pointer anywhere and another app in front (#TBD).

## [1.2.0] - 2026-10-21

### Added

- **Benchmark.** `pnpm bench -- --model provider/id` runs the dry-run review over 12 labeled cases in `bench/cases/` (8 with one seeded bug, 4 known-clean) and prints precision, recall, the verifier's discards, and one row per case. `--runs N` repeats the set to show variance, `--json` writes a results file, and `pnpm bench:compare` compares two of them. It calls a real model, so it never runs in CI (#22).
- **Multi-commit benchmark cases.** A case with a `commits` list reviews the PR again after each later commit, which can also delete files, and publishes every review to an in-process fake GitHub. Eight cases (`fix`, `leave`, `move`, `rewrite-still-buggy`, `partial-fix`, `worse`, `fix-elsewhere`, `regress`) report the false-resolution rate, identity kept, the duplicate-comment rate, and resolution recall. `bench/baselines/` holds the first run, which records how today's reviewer tracks findings (#25).
- **Carried findings in the review body.** A review of a later commit lists the findings from earlier reviews under "Still present from an earlier commit", "Possibly fixed, the cited code changed" and "Outdated, the cited file is gone", each with the commit it was first reported on, at most 20 per section and then "and N more". A body that would exceed GitHub's 65,536-character limit is cut at a line end, with a notice, and keeps its marker. A finding is found again by the code it cites, so it keeps its identity when its lines move, its file is renamed, or its text moves to one other file. A re-reported finding keeps its ID only when the report sits in the same file and category and names the same title where the finding was, cites the same code from the finding's own file, or cites the finding's lines from within three lines of it; a shared helper both cite is no link, and anything else is a new finding, which may repeat a comment but never hides a defect. Migration 055 records which GitHub review carries each finding's inline comment, and the terminal client's finding history gains an optional `basis` per entry. Marking a finding resolved is not built yet, so no finding reaches `RESOLVED`. `bench/baselines/finding-carry-over-2026-10-21.json` records the multi-commit benchmark after this change, and `finding-carry-over-2026-10-21-r2.json` one run after the audit fixes to the link rules (#26).
- **Setup checks in the terminal client.** The daemon sends the `pr-review setup --check` results in `welcome.checks`, an optional field that older clients ignore. Settings lists them under **Setup**, and an empty inbox names the missing checks and their fixes. The client never asks for or sends a secret (#23).

### Fixed

- **Duplicate inline comments on every push.** Each push posted a new inline comment for every finding, including the ones already commented on the last push. An inline comment now goes only to a finding never posted before; a finding reported again, or found unchanged, is listed in the review body instead. A finding whose review failed to post is commented on by the next push, unless its write may have reached GitHub, in which case `pr-review reconcile` decides first. Under `silent_no_findings`, a push posts only when it has a new finding or a first comment on a carried one (#26).
- **Jev skip reason.** `pr-review serve` and `pr-review daemon --allow-commands` record `jev_skipped_no_key` when they skip Jev for lack of `TYPESAFE_API_KEY`, instead of `jev_skipped_private_repo`, which was wrong for public repositories. A per-PR `review` of a private repository still records `jev_skipped_private_repo` (#21).

## [1.1.0] - 2026-10-21

### Added

- **Setup command.** `pr-review setup` checks git, the config file, the model, the GitHub account, Jev, and the terminal client, and offers to log in, pick a default model, and choose a publish mode. `setup --check [--json]` prints the same checks without prompting and exits 1 when a review cannot run. Saving the default model from the `review` picker now writes to `PR_REVIEW_CONFIG` when it is set (#19).

## [1.0.1] - 2026-10-21

### Changed

- **Spinners.** The terminal client marks running work (the PR rail, the live review, the status line and posting to GitHub) with ratatui-spinner's braille spinner (`⣾⣷⣯⣟⡿⢿⣽⣻`) instead of the turning quadrant. The phase steppers show the running phase as a filled dot instead of a spinner. In the live phase bar, the running phase's segment bounces an arc like ratatui-spinner's `BarSpinner` in its `Thick` style, instead of walking a highlight. `--ascii` keeps its glyphs (#13).

## [1.0.0] - 2026-10-21

This is the first release.

### Added

- **Durable reviewer.** The `pr-review review <url>` command reviews one PR as a durable task, with checkpoints after collect context, triage, analyze, verify, prepare and publish. A crash or restart resumes the task where it stopped. Code checks every finding against the diff and the pinned commit before it can be reported (#1).
- **Model detection.** pr-review detects the installed harnesses and their models, and lets you choose a model with `--model` or interactively (#1).
- **GitHub App service.** `pr-review serve` reviews PRs when webhooks arrive. Each webhook's HMAC signature is verified, a lease coordinates the work, and bursts of webhooks are debounced (#3).
- **Exactly-once publication.** Reviews are published through an outbox. Before the first POST, pr-review lists GitHub's reviews to find any it already posted. It commits `sending` before posting, and reconciles against GitHub when a write's result is uncertain (#3).
- **Terminal client.** `pr-review tui` is a Ratatui client with Inbox, Review, Diff, Timeline and Settings views. It opens on the most severe finding, and `w` follows a running review. It supports mouse input, Ink (dark) and Paper (light) palettes with WCAG contrast of at least 4.5, light-background detection over OSC 11, `--ascii` and `NO_COLOR` modes, and a playback mode that runs the showcase with no daemon (#4, #9).
- **Control daemon.** `pr-review daemon` serves the client over a local socket. It speaks version 1 of the protocol, which has a JSON Schema, fixtures and a sequenced event stream (#4).
- **gh account selector.** The client and the daemon detect `gh` accounts without reading tokens, and the client can switch between them (#4).
- **Review actions.** With `pr-review daemon --allow-commands`, the client can start a review (`s`), retry a failed one (`R`) and cancel a running one (`c`). Each action asks a plain question before it is sent (#10).
- **Approve to publish.** With `review.publish_mode: "approval"`, a finished review waits in `AWAITING_APPROVAL`. `p` previews exactly what will be posted, `m` toggles the raw markdown, `y` publishes it once, and `o` opens the posted review (#10).
- **PR titles.** Migration 054 stores each PR's GitHub title, so the live stream shows it from the first event (#10).

### Changed

- The client's footer offers a key only when that key acts in the current view, and gives its room to action keys before the view list (#11).
- The client shows refusals and empty states as plain sentences. Refusals the client makes without asking the daemon are marked "not sent" (#11).
- The client sends any start the daemon may accept, and refuses up front only a start for a head whose review is running or parked (#11).

### Fixed

- The client no longer turns a late terminal reply to the colour query, or an Alt+arrow typed at startup, into keypresses (#11).
- `J`/`K` scrolling stops at the end of the document, and the scroll is clamped again after a resize (#11).
- `j`/`k` load the next page of a paged diff or timeline (#11).
- The daemon sends real code as real code as a finding's evidence, and never fetches from the network. Offline reads need git 2.45 or later, for `GIT_NO_LAZY_FETCH` (#8).
- The client uses a distinct glyph for critical findings, adds a severity legend, and shows the PR in the timeline panel (#7).

### Security

- `pr-review daemon` is read-only by default. It takes no lock and runs no engine until commands are enabled with `--allow-commands` or `control.allow_commands`.
- Before it publishes, `review.publish` checks four things:
  - the review is still waiting for approval;
  - the preview matches the stored payload;
  - the head on GitHub has not moved;
  - the PR is still open.
- Command idempotency keys are bound to each run attempt, so a replayed command never has a second effect.
