# Reviewer control protocol, v1

The daemon (`pr-review daemon`) and the TUI (`pr-review-tui`) exchange newline-delimited JSON over a Unix socket: one
message per line, at most 1 MiB per line. The source of truth is `src/protocol/v1.ts` (TypeBox). Everything under
`schema/`, `fixtures/` and `playback/` is generated by `pnpm protocol:emit`; do not edit those files by hand. A test fails
when they drift from the source.

## Messages

Every message has a `type`. Every client message carries a `requestId`, and the reply echoes it. Server messages that can
also arrive unsolicited (`snapshot`, `resync.required`, `error`) have an optional `requestId`.

| Client → server | Fields | Reply |
| --- | --- | --- |
| `hello` | `protocolVersion` (any integer), `client`, `capabilities[]` | `welcome`, or `error PROTOCOL_MISMATCH` with `supported: [1]` and then the server closes the socket |
| `snapshot.get` | | `snapshot`, then live `event`s |
| `resume` | `streamEpoch`, `afterSequence` | replayed then live `event`s, or `resync.required` |
| `diff.get` | `prId`, `baseSha`, `headSha`, `file?`, `cursor?`, `limit?` (1..500) | `diff.page` |
| `finding.get` | `findingId` | `finding.detail` |
| `publication.get` | `runId` | `publication.preview`, or `error NOT_FOUND` for a run with no stored payload |
| `timeline.get` | `prId?`, `runId?`, `findingId?`, `beforeSequence?`, `limit` (1..500) | `timeline.page` (newest first; pass `nextBeforeSequence` back to page) |
| `settings.get` | | `settings`, from a daemon in `engine` mode; elsewhere `error CAPABILITY_DENIED` with the reason |
| `usage.get` | `by` (`day`, `week` or `month`), `periods?` (1..400), `group?` (`time`, `repo`, `author` or `pr`; `time` when absent) | `usage.report`, from every daemon, a read-only one included (see [Usage](#usage)) |
| `command` | `command`, `params`, `idempotencyKey` | `command.result`. A command the `welcome` did not grant is `rejected` with code `CAPABILITY_DENIED`. |

| Server → client | Fields |
| --- | --- |
| `welcome` | `protocolVersion: 1`, `serverVersion`, `sessionId`, `capabilities[]`, `mode?` (`engine` or `read-only`; absent from older servers), `readOnlyReason?` (display text, present in `read-only` mode), `checks[]?` (see [Setup checks](#setup-checks); absent from older and fixture servers), `streamEpoch`, `latestSequence` |
| `snapshot` | `streamEpoch`, `sequence`, `prs[]`, `runs[]`, `findings[]`, `accounts[]?` (absent from older servers) |
| `event` | see below |
| `resync.required` | `reason` (display text) |
| `diff.page` | `prId`, `baseSha`, `headSha`, `files[]`, `nextCursor?`, `truncated` |
| `finding.detail` | `finding`: a `Finding` plus `explanation`, `reasoningSummary`, `suggestedFix?`, `evidence[]`, `history[]` (each entry a run, the finding state it ended in, and an optional `basis` for why) |
| `publication.preview` | `runId`, `previewId` (the payload hash the approval must name), `headSha`, `body` (the exact review text, marker included), `comments[]` (`path`, `line`, `side: RIGHT`, `body`), `event: COMMENT`, `status` |
| `timeline.page` | `events[]` (sequenced events), `nextBeforeSequence?` |
| `settings` | `model` (`ref`, and `source`: `--model`, `PR_REVIEW_MODEL`, `config` or `default`), `models[]` (`ModelOption`: `ref`, `provider`, `name`, `contextWindow`, `authSource`, `preferred`; preferred first), `configPath` (the file `settings.set` writes), and from this version `summaryTemplate` (`value`: the review body template in force, `isDefault`, `default`: the built-in template, `variables[]`: `name`, `description`, `sample` for every `{{name}}` a template may use) |
| `usage.report` | `by`, `timeZone`, `currency: USD`, `priceSource: catalog`, `buckets[]` (`start`, `end`, `reviews`, `responses`, `input`, `output`, `cacheRead`, `cacheWrite`, `cost`), `totals` (the same counts for the range), `models[]` (the same counts per `model`, costliest first), `group?` (absent from older servers), `groups[]?` (unless `group` is `time`: `key`, `label`, `repository?`, `number?`, `title?`, `prId?`, `author?`, the same counts and `share`) |
| `command.result` | `status: accepted` with `operationId` (and `prId`, `runId` from `review.add`), or `status: rejected` with `code` and `message` (and `prId` when `review.add` names a tracked PR) |
| `error` | `code`, `message`, `supported?` |

Error codes: `UNAUTHORIZED`, `CAPABILITY_DENIED`, `INVALID_TRANSITION`, `REVISION_STALE`, `NOT_FOUND`, `CONFLICT`,
`RATE_LIMITED`, `TEMPORARILY_UNAVAILABLE`, `INTERNAL_ERROR`, `PROTOCOL_MISMATCH`, `INVALID_REQUEST`. The server answers
a line that is not JSON, is over 1 MiB, or fails the client schema with `INVALID_REQUEST`.

Entities are in `schema/v1/{pr,run,finding,finding-detail,evidence,diff-file,account,check,model-option,event}.json`. A run is one engine revision
(`id` is the revision id). `phase` is the engine state: `COLLECT_CONTEXT TRIAGE ANALYZE VERIFY PREPARE_PUBLICATION
AWAITING_APPROVAL PUBLISH RECONCILE COMPLETED FAILED SUPERSEDED`. `AWAITING_APPROVAL` is a run whose review is stored and
parked for a human (publish mode `approval`); its `status` is still `RUNNING`. A `Finding.line` of `null` means a file-level finding.
`Finding.unconfirmed` is `true` when the reviewer suspects the finding but could not show it from the cited code alone.
The server omits it for a confirmed finding, and a client that predates it ignores it.
`Pr.archivedAt` is the time a reader archived the PR. The server sends it only for an archived PR, so a PR that is not
archived reads exactly as before, and a client that predates it ignores it. The server still sends archived PRs, their
runs and their findings; a client leaves archived PRs out of its lists.

## Commands

The command shapes are the only closed objects in the protocol: an unknown param or field makes the command invalid.
The `idempotencyKey` is fixed by the command and its params, so a replayed key is the same request: the server answers
the recorded `operationId` and does nothing again. A key in any other form is `INVALID_REQUEST`.

| `command` | `params` | `idempotencyKey` | `operationId` |
| --- | --- | --- | --- |
| `review.add` | `url` | `review.add:<url>` | `review.add:<runId>` of the run it started |
| `review.start` | `prId`, `expectedHeadSha` | `review.start:<prId>:<expectedHeadSha>` | `review.start:<runId>` of the run started or found |
| `review.again` | `prId`, `expectedHeadSha` | `review.again:<prId>:<expectedHeadSha>` | `review.again:<runId>` of the new run |
| `review.retry` | `runId` | `review.retry:<runId>` | `review.retry:<runId>` |
| `review.cancel` | `runId` | `review.cancel:<runId>` | `review.cancel:<runId>` |
| `review.publish` | `runId`, `previewId`, `expectedHeadSha` | `review.publish:<runId>:<previewId>` | `review.publish:<runId>` |
| `account.select` | `accountId` | `account.select:<accountId>` | `account.select:<journal seq>` |
| `pr.archive` | `prId` | `pr.archive:<prId>` | `pr.archive:<journal seq>` |
| `pr.unarchive` | `prId` | `pr.unarchive:<prId>` | `pr.unarchive:<journal seq>` |
| `daemon.stop` | `pauseReviews` | `daemon.stop` | `daemon.stop` |
| `settings.set` | `model?`, `summaryTemplate?` (string, or `null`) | `settings.set:<model>`, plus `:template:<hash>` when it sets the template | same as the key |

`welcome.capabilities` lists what this daemon grants. A daemon in `read-only` mode (the default, or another pr-review
holds the data dir, or the engine failed to open; `welcome.readOnlyReason` says which) grants only the reader's own
commands: `account.select`, `pr.archive` and `pr.unarchive`.
A daemon started with `--allow-commands` or `control.allow_commands` runs in `engine` mode and grants the review
commands, and `review.publish` only under `review.publish_mode: "approval"`. The `pr-review daemon` process in
`engine` mode also grants `daemon.stop` and `settings.set`; a read-only daemon never does, because its data dir may belong to another
process.
Every command is checked by the server whatever the client showed:

- `review.add`: `url` is a GitHub pull request URL or `owner/repo#N` (`INVALID_REQUEST` otherwise). The daemon reads
  the PR from GitHub with its own account (`NOT_FOUND` when GitHub refuses, naming that account, or saying it has no
  token), the PR must be open (`CONFLICT`), and it must not be tracked already (`CONFLICT` with `prId` set, so the
  client can select it; nothing starts). Then the PR is tracked and its review starts as `pr-review review` starts one,
  under the daemon's `publish_mode`. `accepted` carries `prId` and `runId`; `pr.updated` and `run.started` follow, so
  every client sees the PR appear. A replayed key answers the PR and run it added.
- `review.start`: the PR must be tracked (`NOT_FOUND`), `expectedHeadSha` must be GitHub's head now (`REVISION_STALE`,
  with the live head in the message), the PR must be open, and the head must not already have a finished or parked
  review (`CONFLICT`; `review.again` redoes one). The run then appears through `run.started` and the usual events.
- `review.again`: review the head from scratch, as a new run that reuses nothing of the earlier ones (context,
  routing, candidates) and uses the daemon's current model. The PR must be tracked (`NOT_FOUND`), `expectedHeadSha`
  must be GitHub's open head now (`REVISION_STALE`, `CONFLICT` when closed), and that head must have a review that
  has ended or is parked: `COMPLETED`, `FAILED` (cancelled included), `SUPERSEDED` or `AWAITING_APPROVAL`. It is
  refused with `CONFLICT` while any run of the PR is running (`PUBLISH` and `RECONCILE` included), when the head has
  no run yet (send `review.start`), and while a publication of that head may have reached GitHub (its outbox is
  sending or needs reconciliation). In one transaction every earlier run of that head that has not been superseded
  ends with `run.superseded` (a parked payload is abandoned; nothing had been sent), and the new run starts with
  `run.started`. Findings are tracked across the runs as across heads: one found again is the same finding. The key
  is bound to the head's review-again generation, as a retry's is to its attempt: it replays while the run it opened
  is in flight, and once that run has ended the same key reviews the head again.
- `review.retry`: only from `FAILED` (`INVALID_TRANSITION` elsewhere), through the audited manual retry.
- `review.cancel`: refused with `CONFLICT` in `PUBLISH` and `RECONCILE`, where a GitHub write may be in flight;
  `INVALID_TRANSITION` for a finished run. A parked run fails at once; a running one has its task aborted. Either way
  the run ends `FAILED` with reason `cancelled from the TUI`, unless its head moved meanwhile (`SUPERSEDED`).
- `review.publish`: the run must be `AWAITING_APPROVAL` (`INVALID_TRANSITION`), `previewId` must equal the stored
  payload's hash (`CONFLICT`), and `expectedHeadSha` must be the run's head and GitHub's open head now
  (`REVISION_STALE`; a moved head or closed PR supersedes the run, with nothing posted). Accepted means the audited
  approval is recorded and the exactly-once publisher owns the rest; `review.publication_changed` says what happened.
- `daemon.stop`: while a review runs (a `RUNNING` run outside `AWAITING_APPROVAL`) it is refused with `CONFLICT`, naming
  how many, unless `pauseReviews` is `true`. Accepted is the last message on that connection: the server then closes
  it and the daemon shuts down as on SIGTERM. Running reviews pause and resume on the next engine start, the data-dir
  lock is released, the socket is removed and the process exits 0. A client that got `accepted` knows the daemon
  stopped on request; any other end of the connection is a lost connection.
- `settings.set`: `model` must be one of `settings.models` (`NOT_FOUND`, listing them). While the daemon's own
  `--model` or `PR_REVIEW_MODEL` outranks the config it is refused with `CONFLICT`, since the choice would not survive
  a restart. Accepted means the model is saved as `models.default` in the daemon's config file, other keys kept, and
  every review started afterwards uses it, with no restart. A run in flight keeps its model. The model is part of a
  run's identity, so a head reviewed again with another model gets a new run instead of the stored result.
  `settings.get` reports the change.
  `summaryTemplate` sets the review body template, saved as `review.summary_template`; `null` or `""` restores the
  default and removes the key. It may hold only `{{name}}` placeholders named in `settings.summaryTemplate.variables`
  and at most 4000 characters: an unknown name is `INVALID_REQUEST` naming it. It applies to review bodies prepared
  afterwards; a payload already stored, as a parked approval's, keeps its text, and `publication.get` shows that text.
  The durable marker is always appended after the body, outside the template. A request may carry `model`,
  `summaryTemplate` or both (neither is `INVALID_REQUEST`); both are checked before either is saved. In the key,
  `<model>` is empty when absent, and `<hash>` is the FNV-1a 64-bit hash of the template's UTF-8 bytes as 16 lowercase
  hex digits, or `default` for a reset: `settings.set::template:default`.

## Accounts

An `Account` is `{ id, host, login, state: ok | error, ghActive, selected, scopes[] }`, where `id` is `<host>/<login>`.
The daemon detects accounts with `gh auth status` and stores the selection per data dir. GitHub reads and publishing
use the first of:

1. `GITHUB_TOKEN`, else `GH_TOKEN`, in the daemon's environment, listed as the account `env/GITHUB_TOKEN` or
   `env/GH_TOKEN`. It cannot be selected, and no selection overrides it. gh never sees either variable, so it lists and
   hands out only its stored accounts.
2. The `selected` account. If gh no longer lists it, it is still listed, with state `error`, and GitHub calls fail
   naming it instead of falling back to another identity.
3. gh's active account on `github.com` (`ghActive`).
4. No token: public repositories only.

`account.select` is offered when `welcome.capabilities` contains `account.select`. The server accepts it only on a
connection that is streaming (after `snapshot.get` or `resume`), for a `github.com` account that `gh auth status` lists
now in state `ok`, and while no `GITHUB_TOKEN` or `GH_TOKEN` overrides the selection. Otherwise it answers `rejected` with
`NOT_FOUND` (no such account) or `CONFLICT`. `accepted` only means the selection was journaled. The client shows the
new selection when the `accounts.updated` event arrives, never on `accepted`. Tokens never cross the socket.

## Archiving

`pr.archive` and `pr.unarchive` are a reader preference, not a review action, so every daemon grants them, a read-only
one included. They set or clear `Pr.archivedAt` and journal one row, which streams as `pr.updated` with the PR as it is
now. Like `account.select`, they take effect by state, not by key: archiving an archived PR journals nothing and answers
the `operationId` of the row that archived it, so a duplicate applies once, and archiving again after an unarchive is a
new row. An unknown `prId` is `rejected` with `NOT_FOUND`. Archiving never touches a run: a review in progress goes on.
A PR comes back only when a review is started on it: `review.start`, `review.again`, `review.retry`, and `review.add`
of a PR already tracked (still `CONFLICT`, naming it) clear `archivedAt` and emit `pr.updated`.

## Usage

`usage.get` reads the model usage the engine recorded: one row per model response of a review, written when the response
arrives. Error answers and retries count, since each was a request the provider billed. A resumed review never counts a
response twice, because a response the engine had already stored is not sent again. Reviews that ran before the daemon
recorded usage have no rows, so the history starts at that release.

`usage.report` groups the rows by the daemon's own `timeZone` (an IANA name). A `day` is a local calendar date, a `week`
runs Monday to Sunday (ISO 8601), and a `month` is a calendar month. `buckets` are the last `periods` buckets up to the
one that holds now, oldest first, and an empty bucket is listed with zeros, so a chart has no gaps. Without `periods`
the range is 14 days, 12 weeks or 12 months. `start` and `end` are local dates (`YYYY-MM-DD`), both inside the bucket.
`reviews` counts distinct runs; the token counts and `cost` are sums over `responses`. `input` excludes cached tokens,
which are `cacheRead` and `cacheWrite`. `cost` is in USD at the model's list price in pi-ai's catalog
(`priceSource: catalog`), rounded to 6 decimals: an estimate, and not what a subscription login is billed. `totals` and
`models` cover the whole range.

`group` splits the same range a second way. `time` (the default) sends the buckets alone. `repo`, `author` and `pr` also
send `groups`, costliest first, ties broken by tokens and then by `label`. Each row has the same counts as a bucket and
its `share` of the range's cost (0 when the range cost nothing), so the shares add up to 1 within rounding. `key` is
unique within the breakdown and `label` is the display text. A `repo` row has `repository`, an `author` row has
`author`, and a `pr` row has `repository`, `number`, `title`, `prId` and `author` when it is known. A PR whose author
is not known yet is labelled `Unknown author`, and a response whose PR the daemon no longer has is labelled `Unknown PR`
in every breakdown. The daemon learns a PR's author when it next reads the PR from GitHub. `group` is optional on both
sides. A client that predates it never asks. A server that predates it ignores it and answers over time with no
`group`, which is how a client that asked for a breakdown tells it has none.

## Setup checks

`welcome.checks` is what `pr-review setup --check` reports for the daemon's own environment and data dir: a list of
`{ id, status: ok | warn | missing, detail, fix? }`. `missing` means reviews cannot run, and `warn` means they run with
a limitation. `detail` and `fix` are display text. `id` is open (`git`, `config`, `model`, `github` and `jev` today),
so a client shows an unknown one as it is. The daemon leaves out the `tui` check, since the client asking is the TUI.

The daemon computes the checks for each `hello`, so a client sees them fresh on every connect and reconnect; it never
polls them. They come from the same code as `setup --check`, which never prompts, never fetches a GitHub token and
never reads `TYPESAFE_API_KEY`'s value, so no secret crosses the socket. A check that fails to compute leaves `checks`
out rather than delaying the welcome. The client only displays them: fixing one is `pr-review setup` in a terminal.

## Events

A sequenced event has `streamEpoch`, `sequence` (the journal's `audit_events.seq`), `prevSequence`, `occurredAt`,
`prId?`, `runId?`, `eventType` and `data`:

| `eventType` | ids | `data` | Client applies |
| --- | --- | --- | --- |
| `pr.updated` | `prId` | `Pr` | upsert the PR |
| `run.started`, `review.completed`, `run.superseded`, `run.failed` | `prId`, `runId` | `Run` | upsert the run |
| `review.phase_changed` | `prId`, `runId` | `{ from, to, event, detail }` | set that run's `phase` to `to` |
| `finding.updated` | `prId`, `runId` | `Finding` | upsert the finding |
| `tool.activity` | `prId`, `runId` | `{ tool, summary, span? }` (summary at most 200 chars) | append to the activity feed; a `span` opens, updates or closes that span of the run's waterfall |
| `review.publication_changed` | `prId`, `runId` | `{ runId, status, reviewId?, url? }` with `status` one of `awaiting_approval`, `publishing`, `published`, `uncertain`, `failed` | set that run's publication status; a publication is done only on `published`, never on `command.result accepted` |
| `accounts.updated` | none | `{ accounts }` | replace the account list |
| anything else | optional | any | nothing, but it still advances `lastApplied` |

### Activity sources and spans

`tool.activity` reports every step of a review, so a running one never looks stuck. `tool` is a short source word:

| `tool` | Phase | `summary`, for example |
| --- | --- | --- |
| `phase` | every phase | `analyze started`, `analyze done in 41.2s` |
| `github` | collect, prepare | `fetching PR #1291`, `PR #1291: head f86859b (0.2s)`, `head unchanged (0.3s)` |
| `git` | collect | `cloning acme/shop` or `fetching origin for acme/shop`, `fetched origin in 0.2s`, `diff: 3 files, +6 -3` |
| `jev` | triage | `risk 0.78, security, deep review 84% (0.3s)`, or `skipped: <reason>` |
| `route` | triage | `deep: <reasons>` |
| `model` | analyze | `turn 4 started`, `turn 4: 12.3s, 1.2k output tokens, called read_file x2, search_code` (or `answered`), `turn 4: 3 tool result(s) in 0.4s` |
| a review tool's name | analyze | `read_file src/a.ts @head`, `submit_candidates 3 candidate(s), 0 resolution claim(s)` |
| `verify` | verify | `checking 3 candidate(s)`, `2 kept, 1 discarded (2.3s)`, `kept: <title>`, `discarded: <title> (<reason>)` |
| `prepare` | prepare | `payload: 2 finding(s), 2 inline comment(s), 612-char summary, parks for approval` |

Summaries carry counts, timings, paths and queries, never model text, reasoning or file contents. A daemon journals
at most 10 tool calls and plain lines a second per review and drops the rest; phase, step and model spans always pass.

`span`, when present, is `{ id, parent?, kind, startedAt, endedAt?, outputTokens? }` with `kind` one of `phase`,
`step`, `model` and `tool`. A line without `endedAt` opens the span `id`, or updates it (its summary and
`outputTokens`) when it is already open; the line with `endedAt` closes it. A line with both is a span that opened and
closed at once, as every tool call is. `parent` is the span it ran in: phases have none, a step's is its
`phase:<name>`, a model turn's is `phase:analyze`, and a tool call's is the turn that asked for it. A client that
does not know `span` ignores it; one that does draws the run's waterfall from it. A new attempt of a run
(`run.started`) starts its waterfall again.

`heartbeat` is `{ type: "event", eventType: "heartbeat", streamEpoch, occurredAt }`. It has no sequence, is never
durable, and never changes state. A missed heartbeat means a stale connection, never a failed run.

## Recovery rules

The client keeps `epoch` and `lastApplied`. A snapshot sets both and replaces all state. For each sequenced event:

1. If the client is waiting for a resync, drop the event.
2. If `streamEpoch` differs from `epoch`, drop it and resync.
3. If `sequence <= lastApplied`, it is a duplicate. Drop it.
4. If `prevSequence != lastApplied`, events are missing. Drop it and resync. Do not use `sequence == lastApplied + 1`:
   journal sequences are shared across PRs and may skip.
5. Otherwise apply it and set `lastApplied = sequence`.

To resync, send `snapshot.get` and drop events until the snapshot arrives.

A `resync.required` message also starts a resync. On reconnect the client sends `hello`, then
`resume { streamEpoch, afterSequence: lastApplied }`. The server either replays from there (the first replayed event has
`prevSequence == afterSequence`) or answers `resync.required`. The server sends no `event` before the client's first
`snapshot.get` or `resume`.

## Forward compatibility

Clients ignore unknown fields and unknown `eventType`s. They also map an unknown enum string (a new phase, finding
status or error code) to an "unknown" value instead of failing the whole message. Use `#[serde(other)]` in Rust.

## Text safety

Every string that comes from a repository, a PR or a model may contain terminal control sequences. The server sanitizes
these strings, and the client sanitizes them again before rendering (`src/protocol/sanitize.ts`):

1. Remove whole escape sequences, in both the ESC form and the 8-bit C1 form:
   - CSI: `ESC [` or `0x9B`, then parameter bytes, intermediate bytes and a final byte.
   - OSC, DCS, SOS, PM and APC (`ESC ] P X ^ _` or `0x9D 0x90 0x98 0x9E 0x9F`): up to and including `BEL`, `ESC \` or
     `0x9C`. Without a terminator, the sequence ends at the next ESC or at the end of the string.
   - Any other `ESC` with its intermediate bytes and final byte.
2. Then remove all remaining C0 controls except `\n` and `\t`, plus DEL and all C1 controls.

The fixtures write control bytes as JSON `\u` escapes.

## Fixtures and playback

- `fixtures/<direction>.<name>.json` holds one valid message. The `client.` or `server.` prefix names the schema to
  check it against.
- `fixtures/invalid/*.json` holds messages that must be rejected. Each one has a `.why.txt` file next to it.
- `playback/<name>.ndjson` is a scripted server session. Each line is `{ "delayMs": n, "message": <server message> }`.
  The script ignores what the client sends, except that a line may carry `"after": "<gate>"`: it waits until the
  client sends a command the gate names, which playback answers `accepted`, and only then starts its delay. A gate is
  a command name (`review.publish`) or one command on one target, spelled as its idempotency key
  (`review.cancel:<runId>`). An opened gated line plays ahead of the lines still waiting, so `--playback` numbers the
  events of a script with gates as it plays them. A command no gate names is rejected with `CAPABILITY_DENIED`.
- `playback/<name>.expect.json` is the client state after the whole script: `streamEpoch`, `lastSequence`,
  `resyncRequested`, `toolActivityCount` (the number of activity events applied), and `prs`, `runs` and `findings`
  sorted by `id`, plus `accounts` (`id`, `state`, `ghActive`, `selected`, sorted by `id`) when the script's snapshot
  carries accounts, plus `publications` (the latest `status` per `runId`, sorted) when the script carries a
  `review.publication_changed`. Titles in this file are already sanitized. The reference reducer in
  `tests/protocol.test.ts` produces exactly this state.
- `--playback` answers `diff.get` with the `fixtures/server.diff.page*.json` whose `prId`, `baseSha` and `headSha` match
  (`server.diff.page.last.json` for a request with a `cursor`), `finding.get` with the
  `fixtures/server.finding.detail*.json` whose finding id matches, `publication.get` with
  the `fixtures/server.publication.preview*.json` whose run id matches, and `usage.get` with
  `fixtures/server.usage.report.<by>.json`, a year of usage in `Europe/Berlin` that ignores `periods`. Anything else is
  `NOT_FOUND`.
