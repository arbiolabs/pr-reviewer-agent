# Reviewer control protocol, v1

The daemon (`pr-review daemon`) and the TUI (`pr-review-tui`) exchange newline-delimited JSON over a Unix socket: one
message per line, at most 1 MiB per line. The source of truth is `src/protocol/v1.ts` (TypeBox). Everything under
`schema/`, `fixtures/` and `playback/` is generated by `pnpm protocol:emit`; do not edit those files by hand. A test fails
when they drift from the source.

## Messages

Every message has a `type`. Every client message carries a `requestId`, and the reply echoes it. Server messages that can
also arrive unsolicited (`snapshot`, `resync.required`, `error`) have an optional `requestId`.

| Client → server | Fields | Reply |
| --- | --- | --- |
| `hello` | `protocolVersion` (any integer), `client`, `capabilities[]` | `welcome`, or `error PROTOCOL_MISMATCH` with `supported: [1]` and then the server closes the socket |
| `snapshot.get` | | `snapshot`, then live `event`s |
| `resume` | `streamEpoch`, `afterSequence` | replayed then live `event`s, or `resync.required` |
| `diff.get` | `prId`, `baseSha`, `headSha`, `file?`, `cursor?`, `limit?` (1..500) | `diff.page` |
| `finding.get` | `findingId` | `finding.detail` |
| `publication.get` | `runId` | `publication.preview`, or `error NOT_FOUND` for a run with no stored payload |
| `timeline.get` | `prId?`, `runId?`, `findingId?`, `beforeSequence?`, `limit` (1..500) | `timeline.page` (newest first; pass `nextBeforeSequence` back to page) |
| `command` | `command`, `params`, `idempotencyKey` | `command.result`. A command the `welcome` did not grant is `rejected` with code `CAPABILITY_DENIED`. |

| Server → client | Fields |
| --- | --- |
| `welcome` | `protocolVersion: 1`, `serverVersion`, `sessionId`, `capabilities[]`, `mode?` (`engine` or `read-only`; absent from older servers), `readOnlyReason?` (display text, present in `read-only` mode), `checks[]?` (see [Setup checks](#setup-checks); absent from older and fixture servers), `streamEpoch`, `latestSequence` |
| `snapshot` | `streamEpoch`, `sequence`, `prs[]`, `runs[]`, `findings[]`, `accounts[]?` (absent from older servers) |
| `event` | see below |
| `resync.required` | `reason` (display text) |
| `diff.page` | `prId`, `baseSha`, `headSha`, `files[]`, `nextCursor?`, `truncated` |
| `finding.detail` | `finding`: a `Finding` plus `explanation`, `reasoningSummary`, `suggestedFix?`, `evidence[]`, `history[]` |
| `publication.preview` | `runId`, `previewId` (the payload hash the approval must name), `headSha`, `body` (the exact review text, marker included), `comments[]` (`path`, `line`, `side: RIGHT`, `body`), `event: COMMENT`, `status` |
| `timeline.page` | `events[]` (sequenced events), `nextBeforeSequence?` |
| `command.result` | `status: accepted` with `operationId`, or `status: rejected` with `code` and `message` |
| `error` | `code`, `message`, `supported?` |

Error codes: `UNAUTHORIZED`, `CAPABILITY_DENIED`, `INVALID_TRANSITION`, `REVISION_STALE`, `NOT_FOUND`, `CONFLICT`,
`RATE_LIMITED`, `TEMPORARILY_UNAVAILABLE`, `INTERNAL_ERROR`, `PROTOCOL_MISMATCH`, `INVALID_REQUEST`. The server answers
a line that is not JSON, is over 1 MiB, or fails the client schema with `INVALID_REQUEST`.

Entities are in `schema/v1/{pr,run,finding,finding-detail,evidence,diff-file,account,check,event}.json`. A run is one engine revision
(`id` is the revision id). `phase` is the engine state: `COLLECT_CONTEXT TRIAGE ANALYZE VERIFY PREPARE_PUBLICATION
AWAITING_APPROVAL PUBLISH RECONCILE COMPLETED FAILED SUPERSEDED`. `AWAITING_APPROVAL` is a run whose review is stored and
parked for a human (publish mode `approval`); its `status` is still `RUNNING`. A `Finding.line` of `null` means a file-level finding.

## Commands

The command shapes are the only closed objects in the protocol: an unknown param or field makes the command invalid.
The `idempotencyKey` is fixed by the command and its params, so a replayed key is the same request: the server answers
the recorded `operationId` and does nothing again. A key in any other form is `INVALID_REQUEST`.

| `command` | `params` | `idempotencyKey` | `operationId` |
| --- | --- | --- | --- |
| `review.start` | `prId`, `expectedHeadSha` | `review.start:<prId>:<expectedHeadSha>` | `review.start:<runId>` of the run started or found |
| `review.retry` | `runId` | `review.retry:<runId>` | `review.retry:<runId>` |
| `review.cancel` | `runId` | `review.cancel:<runId>` | `review.cancel:<runId>` |
| `review.publish` | `runId`, `previewId`, `expectedHeadSha` | `review.publish:<runId>:<previewId>` | `review.publish:<runId>` |
| `account.select` | `accountId` | `account.select:<accountId>` | `account.select:<journal seq>` |

`welcome.capabilities` lists what this daemon grants. A daemon in `read-only` mode (the default, or another pr-review
holds the data dir, or the engine failed to open; `welcome.readOnlyReason` says which) grants `account.select` only.
A daemon started with `--allow-commands` or `control.allow_commands` runs in `engine` mode and grants the review
commands, and `review.publish` only under `review.publish_mode: "approval"`.
Every command is checked by the server whatever the client showed:

- `review.start`: the PR must be tracked (`NOT_FOUND`), `expectedHeadSha` must be GitHub's head now (`REVISION_STALE`,
  with the live head in the message), the PR must be open, and the head must not already have a finished or parked
  review (`CONFLICT`). The run then appears through `run.started` and the usual events.
- `review.retry`: only from `FAILED` (`INVALID_TRANSITION` elsewhere), through the audited manual retry.
- `review.cancel`: refused with `CONFLICT` in `PUBLISH` and `RECONCILE`, where a GitHub write may be in flight;
  `INVALID_TRANSITION` for a finished run. A parked run fails at once; a running one has its task aborted. Either way
  the run ends `FAILED` with reason `cancelled from the TUI`, unless its head moved meanwhile (`SUPERSEDED`).
- `review.publish`: the run must be `AWAITING_APPROVAL` (`INVALID_TRANSITION`), `previewId` must equal the stored
  payload's hash (`CONFLICT`), and `expectedHeadSha` must be the run's head and GitHub's open head now
  (`REVISION_STALE`; a moved head or closed PR supersedes the run, with nothing posted). Accepted means the audited
  approval is recorded and the exactly-once publisher owns the rest; `review.publication_changed` says what happened.

## Accounts

An `Account` is `{ id, host, login, state: ok | error, ghActive, selected, scopes[] }`, where `id` is `<host>/<login>`.
The daemon detects accounts with `gh auth status` and stores the selection per data dir. GitHub reads and publishing
use the first of:

1. `GITHUB_TOKEN`, else `GH_TOKEN`, in the daemon's environment, listed as the account `env/GITHUB_TOKEN` or
   `env/GH_TOKEN`. It cannot be selected, and no selection overrides it. gh never sees either variable, so it lists and
   hands out only its stored accounts.
2. The `selected` account. If gh no longer lists it, it is still listed, with state `error`, and GitHub calls fail
   naming it instead of falling back to another identity.
3. gh's active account on `github.com` (`ghActive`).
4. No token: public repositories only.

`account.select` is offered when `welcome.capabilities` contains `account.select`. The server accepts it only on a
connection that is streaming (after `snapshot.get` or `resume`), for a `github.com` account that `gh auth status` lists
now in state `ok`, and while no `GITHUB_TOKEN` or `GH_TOKEN` overrides the selection. Otherwise it answers `rejected` with
`NOT_FOUND` (no such account) or `CONFLICT`. `accepted` only means the selection was journaled. The client shows the
new selection when the `accounts.updated` event arrives, never on `accepted`. Tokens never cross the socket.

## Setup checks

`welcome.checks` is what `pr-review setup --check` reports for the daemon's own environment and data dir: a list of
`{ id, status: ok | warn | missing, detail, fix? }`. `missing` means reviews cannot run, and `warn` means they run with
a limitation. `detail` and `fix` are display text. `id` is open (`git`, `config`, `model`, `github` and `jev` today),
so a client shows an unknown one as it is. The daemon leaves out the `tui` check, since the client asking is the TUI.

The daemon computes the checks for each `hello`, so a client sees them fresh on every connect and reconnect; it never
polls them. They come from the same code as `setup --check`, which never prompts, never fetches a GitHub token and
never reads `TYPESAFE_API_KEY`'s value, so no secret crosses the socket. A check that fails to compute leaves `checks`
out rather than delaying the welcome. The client only displays them: fixing one is `pr-review setup` in a terminal.

## Events

A sequenced event has `streamEpoch`, `sequence` (the journal's `audit_events.seq`), `prevSequence`, `occurredAt`,
`prId?`, `runId?`, `eventType` and `data`:

| `eventType` | ids | `data` | Client applies |
| --- | --- | --- | --- |
| `pr.updated` | `prId` | `Pr` | upsert the PR |
| `run.started`, `review.completed`, `run.superseded`, `run.failed` | `prId`, `runId` | `Run` | upsert the run |
| `review.phase_changed` | `prId`, `runId` | `{ from, to, event, detail }` | set that run's `phase` to `to` |
| `finding.updated` | `prId`, `runId` | `Finding` | upsert the finding |
| `tool.activity` | `prId`, `runId` | `{ tool, summary }` (summary at most 200 chars) | append to the activity feed |
| `review.publication_changed` | `prId`, `runId` | `{ runId, status, reviewId?, url? }` with `status` one of `awaiting_approval`, `publishing`, `published`, `uncertain`, `failed` | set that run's publication status; a publication is done only on `published`, never on `command.result accepted` |
| `accounts.updated` | none | `{ accounts }` | replace the account list |
| anything else | optional | any | nothing, but it still advances `lastApplied` |

`heartbeat` is `{ type: "event", eventType: "heartbeat", streamEpoch, occurredAt }`. It has no sequence, is never
durable, and never changes state. A missed heartbeat means a stale connection, never a failed run.

## Recovery rules

The client keeps `epoch` and `lastApplied`. A snapshot sets both and replaces all state. For each sequenced event:

1. If the client is waiting for a resync, drop the event.
2. If `streamEpoch` differs from `epoch`, drop it and resync.
3. If `sequence <= lastApplied`, it is a duplicate. Drop it.
4. If `prevSequence != lastApplied`, events are missing. Drop it and resync. Do not use `sequence == lastApplied + 1`:
   journal sequences are shared across PRs and may skip.
5. Otherwise apply it and set `lastApplied = sequence`.

To resync, send `snapshot.get` and drop events until the snapshot arrives.

A `resync.required` message also starts a resync. On reconnect the client sends `hello`, then
`resume { streamEpoch, afterSequence: lastApplied }`. The server either replays from there (the first replayed event has
`prevSequence == afterSequence`) or answers `resync.required`. The server sends no `event` before the client's first
`snapshot.get` or `resume`.

## Forward compatibility

Clients ignore unknown fields and unknown `eventType`s. They also map an unknown enum string (a new phase, finding
status or error code) to an "unknown" value instead of failing the whole message. Use `#[serde(other)]` in Rust.

## Text safety

Every string that comes from a repository, a PR or a model may contain terminal control sequences. The server sanitizes
these strings, and the client sanitizes them again before rendering (`src/protocol/sanitize.ts`):

1. Remove whole escape sequences, in both the ESC form and the 8-bit C1 form:
   - CSI: `ESC [` or `0x9B`, then parameter bytes, intermediate bytes and a final byte.
   - OSC, DCS, SOS, PM and APC (`ESC ] P X ^ _` or `0x9D 0x90 0x98 0x9E 0x9F`): up to and including `BEL`, `ESC \` or
     `0x9C`. Without a terminator, the sequence ends at the next ESC or at the end of the string.
   - Any other `ESC` with its intermediate bytes and final byte.
2. Then remove all remaining C0 controls except `\n` and `\t`, plus DEL and all C1 controls.

The fixtures write control bytes as JSON `\u` escapes.

## Fixtures and playback

- `fixtures/<direction>.<name>.json` holds one valid message. The `client.` or `server.` prefix names the schema to
  check it against.
- `fixtures/invalid/*.json` holds messages that must be rejected. Each one has a `.why.txt` file next to it.
- `playback/<name>.ndjson` is a scripted server session. Each line is `{ "delayMs": n, "message": <server message> }`.
  The script ignores what the client sends, except that a line may carry `"after": "<gate>"`: it waits until the
  client sends a command the gate names, which playback answers `accepted`, and only then starts its delay. A gate is
  a command name (`review.publish`) or one command on one target, spelled as its idempotency key
  (`review.cancel:<runId>`). An opened gated line plays ahead of the lines still waiting, so `--playback` numbers the
  events of a script with gates as it plays them. A command no gate names is rejected with `CAPABILITY_DENIED`.
- `playback/<name>.expect.json` is the client state after the whole script: `streamEpoch`, `lastSequence`,
  `resyncRequested`, `toolActivityCount` (the number of activity events applied), and `prs`, `runs` and `findings`
  sorted by `id`, plus `accounts` (`id`, `state`, `ghActive`, `selected`, sorted by `id`) when the script's snapshot
  carries accounts, plus `publications` (the latest `status` per `runId`, sorted) when the script carries a
  `review.publication_changed`. Titles in this file are already sanitized. The reference reducer in
  `tests/protocol.test.ts` produces exactly this state.
- `--playback` answers `diff.get` with the `fixtures/server.diff.page*.json` whose `prId`, `baseSha` and `headSha` match
  (`server.diff.page.last.json` for a request with a `cursor`), `finding.get` with the
  `fixtures/server.finding.detail*.json` whose finding id matches, and `publication.get` with
  the `fixtures/server.publication.preview*.json` whose run id matches. Anything else is `NOT_FOUND`.
